# LeadPilot API

FastAPI backend for LeadPilot. This is a **starter scaffold**: the architecture,
wiring, and tooling are complete, but no domain models exist yet.

## Requirements

- Python 3.12 (the venv is already created at `.venv`)
- MySQL 8 (reached over an SSH tunnel; see below), or SQLite for a zero-setup run
- Docker (optional)

## Getting started

```powershell
# 1. Activate the venv
.\.venv\Scripts\Activate.ps1

# 2. Install dependencies
pip install -r requirements-dev.txt

# 3. Create your local config
Copy-Item .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(32))"   # paste into SECRET_KEY

# 4. Open the database tunnel (separate terminal, leave running)
.\scripts\tunnel.ps1

# 5. Run
uvicorn app.main:app --reload
```

Docs are then at <http://localhost:8000/docs>.

### Database access

MySQL runs on the application server and listens on **its own loopback only** —
it is not exposed to the internet. Local development reaches it through an SSH
tunnel:

```powershell
.\scripts\tunnel.ps1          # 127.0.0.1:3306 -> server's MySQL, via ubuntu@43.157.81.74
```

Leave that terminal open. `.env` already points at `127.0.0.1:3306`, so no
config changes are needed — the tunnel makes that address correct.

Key authentication is already set up, so this does **not** prompt for a
password. If it ever does, re-install your public key:

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh ubuntu@43.157.81.74 `
  "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

### Every time you restart work

The tunnel does not survive a reboot, sleep, or closing its terminal. When the
API starts returning `Failed to fetch` or `Errno 10061`, the tunnel is down.

```powershell
.\scripts\tunnel.ps1              # terminal 1 — leave open, Ctrl+C to stop
uvicorn app.main:app --reload     # terminal 2
```

To check whether it is up:

```powershell
Get-NetTCPConnection -LocalPort 3306 -State Listen   # no output = tunnel down
curl http://localhost:8000/api/v1/health/ready       # 503 = database unreachable
```

When the backend is deployed **on** that server, no tunnel is involved and
`127.0.0.1` is already correct.

To work without any database access at all, set this in `.env`:

```env
DATABASE_URL=sqlite+aiosqlite:///./leadpilot.db
```

## Project layout

```
app/
  main.py              # App factory, middleware, lifespan
  api/
    deps/              # Injectable dependencies (DbSession, CurrentUser, Pagination)
    v1/
      router.py        # Aggregates all v1 routes
      routes/          # One module per resource
  core/
    config.py          # Settings from environment
    security.py        # Password hashing, JWT encode/decode
    exceptions.py      # Error types + handlers (one JSON error shape)
    logging.py         # structlog setup
  db/
    base.py            # Declarative Base, TimestampMixin, model registry
    session.py         # Async engine + session factory
    migrations/        # Alembic
  models/              # SQLAlchemy ORM models
  schemas/             # Pydantic request/response models
  repositories/        # Query logic, one per model
  services/            # Business rules, owns transactions
tests/
docker/
```

### The layering rule

```
route -> service -> repository -> model
```

- **Routes** parse input and return schemas. No business logic, no queries.
- **Services** hold the rules and call `commit()`. They raise `AppError`
  subclasses; the handlers in `core/exceptions.py` turn those into JSON.
- **Repositories** own all SQLAlchemy. Nothing above this layer writes a query.

Every error response shares one shape:

```json
{ "error": { "code": "not_found", "message": "...", "details": null } }
```

## Adding a resource

1. `app/models/lead.py` — the ORM model, then import it in `app/db/base.py`
   so Alembic autogenerate can see it.
2. `app/schemas/lead.py` — `LeadCreate`, `LeadUpdate`, `LeadRead`.
3. `app/repositories/lead.py` — `class LeadRepository(BaseRepository[Lead])`.
4. `app/services/lead.py` — the rules.
5. `app/api/v1/routes/leads.py` — the endpoints, then register the router in
   `app/api/v1/router.py`.
6. `alembic revision --autogenerate -m "add leads"` then `alembic upgrade head`.

## Migrations

The tunnel must be open first — Alembic connects to the real database.

```powershell
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
alembic downgrade -1
```

The `leadpilot` schema is currently **empty** (no tables). The first migration
will be generated once the first model exists in `app/models/`.

Review every autogenerated migration before applying it — autogenerate misses
renames and some constraint changes.

## Connecting the frontend

The Vue app reads `VITE_API_BASE_URL` (default `/api`) and sends
`Authorization: Bearer <token>`, taking the token from a **non-HttpOnly**
`accessToken` cookie it sets itself. So the login endpoint must return the token
in the JSON body — an HttpOnly cookie would be invisible to it.

In the frontend's `.env`:

```env
VITE_API_BASE_URL=http://localhost:8000/api/v1
```

`BACKEND_CORS_ORIGINS` in this project's `.env` already allows the Vite dev
origin (`http://localhost:5173`).

## The n8n lead-search workflow

A Lead Radar search is not executed by this API. `POST /lead-radar/search`
opens a run row, POSTs the job to `N8N_WEBHOOK_URL`, and returns. From then on
n8n does the work and **calls back** into this API; the browser only watches.
That is why a user can close the tab: the workflow keeps running, the results
are saved and billed when they arrive, and an in-app notification is created
for the user to find on their next visit (and pushed live if a tab is open).

### The callbacks must reach this API

`PUBLIC_API_URL` is the base of every callback URL handed to n8n
(`progress_url`, `results_url`). It has to be reachable **from the n8n host**.
With n8n on the VM and the API on a laptop that means a tunnel:

```powershell
ngrok http 8000
# then put the https URL it prints into .env as PUBLIC_API_URL and restart
```

A free ngrok URL changes every time the agent restarts, and the old one
answers `ERR_NGROK_3200` -- every callback from n8n is then lost and the run
sits at "running" until the sweeper closes it. Reserve a static domain in the
ngrok dashboard and start it with `ngrok http --url=<your-domain> 8000` so
`PUBLIC_API_URL` (and the frontend's `VITE_API_BASE_URL`) stop changing.

### What n8n sends

Each progress node POSTs to `{{ $json.progress_url }}` with header
`X-LeadPilot-Run-Token: {{ $json.progress_token }}`:

```json
{
  "stage": "searching_companies",
  "count": 42,
  "message": "Searching web for target companies",
  "execution_id": "{{ $execution.id }}"
}
```

`stage` is one of `searching_companies`, `ai_analysing`, `domain_search`,
`finding_decision_makers`, `finding_emails`, `verifying_contacts`; add
`"status": "completed"` on the last one. `execution_id` is optional but send
it on every checkpoint -- see the error trigger below for why. n8n's HTTP
Request node runs once per input item, so tick **Execute Once** on these nodes
or a 28-item input fires 28 identical callbacks.

The results node POSTs the full company list to `{{ $json.results_url }}` with
the same token header (see `SearchResultsRequest` in `app/schemas/lead.py`).

### The Error Trigger workflow

A separate workflow with an *Error Trigger* node catches any failure of the
lead-search workflow. Its HTTP Request node POSTs to
`<PUBLIC_API_URL>/api/v1/lead-radar/error` with exactly:

```json
{
  "workflow_id": "{{ $json.workflow.id }}",
  "execution_id": "{{ $json.execution.id }}",
  "error_message": "{{ $json.execution.error.message }}",
  "last_node_executed": "{{ $json.execution.lastNodeExecuted }}"
}
```

That payload carries no run id, so the API works out whose search it was:

1. `run_id` + `progress_token` in the body, if the workflow can pass them
   through (exact);
2. `execution_id`, matched against the id the progress callbacks reported
   (exact -- this is why every checkpoint should send `execution_id`);
3. otherwise the single search currently in flight, if there is exactly one.
   With two or more running, nothing is guessed: the failure is stored, and
   the sweeper closes the dead run a little later.

The response says which rule matched (`attributed_by`). An attributed failure
marks the run failed, stops the tracker, records the failing node, and
notifies the user. With `N8N_WEBHOOK_SECRET` set, the error node must also
send that secret in the `N8N_WEBHOOK_HEADER` header (default
`X-LeadPilot-Token`); without a secret the endpoint stays open so an outage
is never silently dropped.

### Runs the workflow never finishes

A background sweeper (started with the app, every
`LEAD_SEARCH_SWEEP_INTERVAL_SECONDS`) fails:

- a run with no checkpoint for `LEAD_SEARCH_STALE_MINUTES` (default 30);
- a run whose last checkpoint said "completed" but whose results did not
  arrive within `LEAD_SEARCH_RESULTS_TIMEOUT_MINUTES` (default 15) -- nothing
  was saved or charged, so "failed" is the honest state.

The user gets the same failure notification as for a reported error.

## What is intentionally left unimplemented

`app/models/` is empty, and the `auth`/`users` route bodies raise
`NotImplementedError`. The auth contract (register/login/refresh/me), the
`BaseRepository`, and `BaseService` are in place to build against — add a `User`
model and wire the TODO in `app/api/deps/auth.py` to a real lookup.
